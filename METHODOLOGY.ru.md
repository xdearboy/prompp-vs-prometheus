# Методика

## Что сравнивается

Три движка, по одному за раз, на одной ноде:

- Deckhouse Prom++ 0.8.15, форк Prometheus с head и WAL на C++ и PromQL-движком с
  семантикой range-селекторов из 3.x
- Prometheus 3.15.0
- Prometheus 2.55.1

Каждый запускается как StatefulSet в одной реплике с томом данных `emptyDir` на 30 GiB
в namespace бенчмарка. Без репликации, без `ServiceMonitor`, без связи с мониторингом
кластера. Движок ничего не скрейпит, он только принимает remote write.

## Правила честности

1. **По одному движку.** Они не конкурируют за CPU и пропускную способность памяти.
2. **Одинаковый вход.** Один seed, одна раскладка лейблов, одно число серий и одни и те
   же временные метки сэмплов.
3. **Одинаковая конфигурация.** Один конфиг, одни флаги, одни лимиты `2000m` / `6Gi`.
4. **Одинаковый рантайм Go.** Каждый движок получает `GOMEMLIMIT=5529MiB` и
   `GOMAXPROCS=2` через окружение. По умолчанию они разные: у Prom++ 0.8.15 и
   Prometheus 2.55.1 `auto-gomemlimit` и `auto-gomaxprocs` спрятаны за опциональными
   feature-флагами, Prometheus 3.x включает оба. Без закрепления движки на 2.x работали
   бы без лимита памяти Go и, если собраны Go старше 1.25, с одним процессором Go на
   каждое ядро ноды при квоте в два ядра. Значения, которые движок отдаёт через
   `/api/v1/status/runtimeinfo`, сохраняются с каждым сэмплом ресурсов и показаны в
   отчёте.
5. **Чистое состояние.** StatefulSet и том удаляются между движками, поэтому никто не
   наследует чужой WAL и блоки.
6. **Одинаковые запросы.** Один набор PromQL при одних и тех же уровнях параллельности,
   в один и тот же момент времени, на данных одного объёма и формы.
7. **Прибитая нода.** У каждого объекта задан `nodeName`, поэтому ядро, page cache и
   иерархия cgroup одинаковы для всех.

## Фазы

| фаза | что происходит |
|---|---|
| ingest | наращиваем активные серии: 50k, 200k, 500k, на каждом шаге держим нагрузку |
| settle | пауза 30 секунд, чтобы снять статистику head и размер диска |
| query | гоняем каждый запрос набора при каждом уровне параллельности |
| dump | хешируем результат каждого запроса для проверки равенства |

## Что измеряется

- **Пропускная способность записи.** Реально достигнутые сэмплы в секунду на шаге.
- **Задержка запроса.** p50 и p99 на один запрос remote write.
- **Статистика head.** Серии, чанки и пары лейблов из API самого движка.
- **Память.** `process_resident_memory_bytes` движка и working set cgroup из cAdvisor
  через прокси kubelet.
- **CPU.** Скорость счётчика CPU контейнера из cAdvisor, запасной вариант
  `process_cpu_seconds_total`, замер каждые две секунды.
- **Диск.** Размеры каталога данных, WAL и блоков из сайдкара, который монтирует тот же
  том, каждые 15 секунд. Шагу достаётся последний замер внутри него.
- **Задержка запросов.** Каждый запрос отдельно: один прогревочный запрос без замера,
  потом `c` воркеров повторяют его, пока не выйдет бюджет времени и не наберётся
  минимальное число запросов. В отчёте p50, p99 и число запросов по каждому запросу, а
  также геометрические средние по всем запросам, чтобы несколько range-запросов в
  секунды не перевешивали остальные. Для каждого набора и уровня параллельности
  работает отдельный сборщик ресурсов, поэтому CPU и память относятся только к этому
  запуску.
- **Равенство результатов.** sha256 канонизированного результата каждого запроса по
  движкам.

Показатели на серию делят последний замер шага на число активных серий этого шага. Это
число, которое растёт вместе с парком.

## Повторные прогоны

Один прогон не показывает разброс. Опубликованные результаты — 12 полных прогонов, они
стартовали каждые четыре часа в течение двух суток из пода внутри кластера. Агрегат
берёт медиану каждого показателя и приводит минимум, максимум и разброс в долях
медианы. Самый быстрый и самый медленный прогоны отличаются меньше чем на 8 %,
исключение — working set у Prom++ (12 %), а разница между движками в несколько раз
больше.

## Угрозы валидности

- **Общая нода.** На ней работают компоненты control plane. Запуск по одному движку
  ограничивает эту помеху, но не убирает её. Она задевает все движки примерно
  одинаково и добавляет разброс. Повторные прогоны в разное время суток нужны, чтобы
  показать, насколько он велик.
- **WAL не сравнивается один в один.** У Prom++ свой формат WAL, у апстримных движков
  по умолчанию сжатие snappy. Цифры по диску и WAL сравнивают то, что получает
  пользователь из коробки, а не одинаковое кодирование.
- **`GOMEMLIMIT` покрывает только кучу Go.** Prom++ держит почти весь head в памяти C++
  под управлением jemalloc, на неё лимит Go не действует. Лимит закреплён ради
  одинакового поведения Go, а не чтобы ограничить общую память.
- **Одна нода, одна реплика.** Стоимость репликации не измеряется.
- **Короткие шаги.** Шаг нагрузки длится минуты, а не часы, поэтому компакция, повторное
  использование mmap и долгие хвосты аллокатора затрагиваются лишь отчасти.
- **Мало запросов у медленных запросов.** Range-запрос в секунды получает только
  минимальное число запросов. Его p99 близок к максимуму, сравнивать лучше медиану.
- **Семантика range-селекторов.** Prometheus 3.0 сделал range-селекторы
  левооткрытыми. На пяти запросах с `rate` и `_over_time` Prom++ 0.8.15 и Prometheus
  3.15.0 совпадают друг с другом и отличаются от 2.55.1, потому что 2.55.1 учитывает
  сэмпл, лежащий ровно на левой границе окна. Отчёт говорит об этом рядом с таблицей
  равенства. В `promql/engine.go` Prom++ отбрасывает сэмплы с `T <= mint`, 2.55.1 — с
  `T < mint`.
- **Синтетические данные.** Генератор даёт реалистичную кардинальность лейблов и смесь
  gauge и counter, но это не продовый скрейп. На реальных наборах лейблов планы
  запросов ведут себя иначе.

## Корректность

Цифры пропускной способности ничего не значат, если движок потерял сэмплы. Набор
данных привязан к фиксированной эпохе, каждый движок получает одни и те же байты, а
результат каждого запроса канонизируется и хешируется. Разный дайджест сообщается как
расхождение, а не усредняется.

Харнес также отказывается строить отчёт из неполных данных: после каждого движка
артефакты копируются из пода, и `run.sh` останавливается, если нужного отчёту файла нет
или он пустой.

## Воспроизводимость

Харнес записывает описание ноды, точные образы, список флагов и заданное окружение в
`results/<run-id>/run.json`. Временные метки, seed и рампа — явные входные параметры,
поэтому два прогона с одинаковыми входами записывают одни и те же сэмплы в одни и те же
окна запросов.
