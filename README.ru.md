# Prom++ против Prometheus

[![ci](https://github.com/xdearboy/prompp-vs-prometheus/actions/workflows/ci.yml/badge.svg)](https://github.com/xdearboy/prompp-vs-prometheus/actions/workflows/ci.yml)

Бенчмарк Deckhouse Prom++ 0.8.15 против Prometheus 3.15.0 и 2.55.1. Движки идут
по одному, в одной реплике, на одной ноде, с одинаковыми лимитами (2 CPU, 6 GiB),
одинаковыми настройками рантайма Go и одними и теми же синтетическими данными.

## Результаты

500 000 активных серий, 27,4 млн сэмплов на движок, 38 запросов PromQL. Числа —
медиана 12 полных прогонов: один каждые четыре часа в течение двух суток. Между самым
быстрым и самым медленным прогоном разброс меньше 8 %, кроме рабочего набора
Prom++ (12 %). Подробности: [AGGREGATE.md](runs/series-20261006/AGGREGATE.md).

![в сравнении с Prometheus 3.15.0](runs/series-20261006/20261006T210616Z/charts/summary.svg)

| при 500k серий | Prom++ 0.8.15 | Prometheus 3.15.0 | Prometheus 2.55.1 |
|---|---|---|---|
| резидентная память | **255 MiB** | 1,11 GiB | 1,09 GiB |
| working set cgroup | **176 MiB** | 1,06 GiB | 1,03 GiB |
| CPU при записи | **0,05 ядра** | 0,19 | 0,23 |
| каталог данных | 281 MiB | 303 MiB | 303 MiB |

Задержка запросов, геометрическое среднее медиан по всем запросам:

| параллельность | Prom++ 0.8.15 | Prometheus 3.15.0 | Prometheus 2.55.1 |
|---|---|---|---|
| 1 | **298 мс** | 348 мс | 345 мс |
| 4 | **682 мс** | 828 мс | 839 мс |
| 16 | **2,53 с** | 3,35 с | 3,46 с |

Главная разница в памяти. Запросы быстрее на 15–25 %, диск примерно одинаковый.
33 из 38 запросов возвращают побайтно одинаковые результаты на всех трёх движках.
Остальные пять — range-запросы с `rate` и `_over_time`: Prom++ 0.8.15 считает
range-селекторы левооткрытыми, как Prometheus 3.x, а 2.55.1 учитывает сэмпл, лежащий
ровно на левой границе окна.

## Движки

| имя | образ | заметки |
|---|---|---|
| `prompp-0815` | `mirror.gcr.io/prompp/prompp:0.8.15` | head и WAL на C++, range-селекторы как в 3.x |
| `prom-3150` | `quay.io/prometheus/prometheus:v3.15.0` | текущий апстрим |
| `prom-2551` | `quay.io/prometheus/prometheus:v2.55.1` | закрытые range-селекторы |

Все три получают одинаковые флаги и одинаковые настройки рантайма через окружение:
`GOMEMLIMIT=5529MiB` (90 % от лимита 6 GiB) и `GOMAXPROCS=2`. Без них движки
нельзя сравнивать: у Prom++ 0.8.15 и Prometheus 2.55.1 `auto-gomemlimit` и
`auto-gomaxprocs` спрятаны за опциональными feature-флагами, а Prometheus 3.x
включает оба. Отчёт показывает значения, которые движок сам отдаёт через
`/api/v1/status/runtimeinfo`, так что закрепление проверяется, а не предполагается.
Список движков лежит в `internal/engines`, тест следит, чтобы манифесты с ним совпадали.

## Структура

```text
tools/          сабмодуль github.com/xdearboy/prom-loadgen: loadgen, querybench,
                collector, генератор серий, клиент remote write, схема результатов
cmd/meta        метаданные прогона
cmd/report      отчёт в markdown и svg по одному прогону
cmd/aggregate   медиана и разброс по многим прогонам
internal/       реестр движков, генератор отчётов и графиков
deploy/         манифесты kustomize, runner.yaml для раннера в кластере
scripts/        harness, run, series, runner, teardown, preflight, node overlay
runs/           опубликованные результаты
  series-20261006/   двенадцать прогонов и их агрегат; у первого прогона лежат сырые
                     сэмплы ресурсов, у остальных только итоги
```

Клонировать с `git clone --recurse-submodules` или выполнить `git submodule update --init`.

## Что нужно

- `kubectl` с kustomize v5 и контекст кластера, в который можно писать
- Go 1.24 или новее
- нода, к которой можно прибить бенчмарк
- свободное место на этой ноде под emptyDir на 30 GiB

Собирать образы не нужно: утилиты кросс-компилируются под linux/amd64 и копируются в
под harness через `kubectl cp`.

## Запуск

```sh
export BENCH_NODE=<нода>

RUN_ID=$(date -u +%Y%m%dT%H%M%SZ) scripts/node-overlay.sh
scripts/harness.sh
RUN_ID="$RUN_ID" scripts/run.sh
scripts/teardown.sh --yes
```

`node-overlay.sh` собирает оверлей, который прибивает каждый движок к `$BENCH_NODE`.
Он лежит в `overlays/local/`, а это в `.gitignore`, поэтому имя реальной ноды в
репозиторий не попадает. В закоммиченных манифестах стоит `bench-node-placeholder`, и
`scripts/preflight.sh` падает, если он дожил до собранного манифеста.

### Повторные прогоны

Один прогон ничего не говорит о разбросе. `scripts/series.sh` запускает прогон каждые
`PERIOD_HOURS` (по умолчанию 4) всего `RUNS` раз (по умолчанию 12) и пишет медиану,
минимум и максимум по всем завершённым прогонам в `results/AGGREGATE.md`. Прогон идёт
около 2,5 часа, поэтому период должен быть больше.

`scripts/runner.sh` запускает всю серию из небольшого пода внутри кластера, так что
машина, с которой стартовали, может быть выключена:

```sh
export BENCH_NODE=<нода>
scripts/harness.sh
scripts/runner.sh
kubectl -n prompp-bench exec bench-runner -- tail /work/series.log
kubectl cp prompp-bench/bench-runner:/work/results ./results
```

### Переменные

| переменная | по умолчанию | что делает |
|---|---|---|
| `BENCH_NODE` | обязательна | нода для движков и harness |
| `BENCH_NAMESPACE` | `prompp-bench` | namespace |
| `ENGINES` | все три | имена движков через пробел |
| `RAMP` | `50000:300,200000:480,500000:600` | шаги `серии:секунды` |
| `SEED` | `20261005` | seed генерации серий |
| `INTERVAL` | `15s` | интервал сэмплов |
| `CONCURRENCIES` | `1 4 16` | параллельные запросы одного и того же запроса |
| `SUITES` | `heavy` | наборы запросов, `heavy` включает `core` |
| `PER_QUERY` | `10s` | бюджет времени на запрос и уровень параллельности |
| `MIN_RUNS` | `5` | замеров на запрос, даже если бюджет вышел |
| `WARMUP` | `1` | прогревочных запросов перед замером |
| `EPOCH_MS` | `1767225600000` | время первого сэмпла |

## Что остаётся после прогона

```text
results/<run-id>/
  run.json                                   нода, движки, версия harness
  <engine>/ingest.json                       пропускная способность, задержки, head по шагам
  <engine>/samples.ingest.jsonl              сэмплы ресурсов во время записи
  <engine>/samples.query-<suite>-c<n>.jsonl  сэмплы ресурсов по каждому запуску запросов
  <engine>/query-<suite>-c<n>.json
  <engine>/dump-<suite>.json                 sha256 каждого результата запроса
  <engine>/disk.jsonl                        каталог данных, WAL и блоки во времени
  REPORT.md, charts/*.svg                    генерируются
```

`run.sh` останавливается, если нужного отчёту файла нет или он пустой после копирования
из пода, и заменяет имя ноды на `bench-node` везде, так что каталог прогона можно
публиковать как есть.

## Что сравнивает отчёт

Память и CPU на активную серию, пропускную способность записи, задержку каждого запроса
при каждой параллельности и равенство результатов. Каждый запрос измеряется отдельно:
один прогревочный запрос, потом воркеры повторяют его, пока не кончится бюджет времени.
В таблицах p50, p99 и число замеров; в итогах геометрические средние, чтобы несколько
range-запросов в секунды не перевешивали остальные. Проверка равенства защищает от
сравнения движков, один из которых тихо потерял данные: все получают один и тот же
закреплённый набор, а результат каждого запроса хешируется.

Правила честности и угрозы валидности описаны в [METHODOLOGY.ru.md](METHODOLOGY.ru.md).
